## Delivered

- Extraction v1 prompts preserve operators, units, counting semantics, service vocabulary,
  scope and modality. Document text is treated as data rather than instructions.
- Extraction output is validated against the named source field. Invalid quotes and
  malformed numeric/qualitative constraints get one repair attempt, then fail closed.
- Semantic comparison receives scope/modality context and must cite an actual supplied
  decision. Missing/invented evidence cannot support either a conflict or a clean pass.
- Deterministic comparison checks decision quotes too, including cached constraints.
  Unknown service, partial environment coverage and uncertain conditions need review.
  Advisory/optional constraints do not become confirmed contradictions.
- Partial decision-extraction failures cannot create a clean pass. A failed comparison
  for one claim no longer discards supported conflicts on other claims.
- Golden data expanded from 15 to 30 scenarios (S16–S30), with one accepted cache-TTL
  recommendation. Existing S01–S15 data and expected outcomes are unchanged.
- `eval/score-scenario.ts` scores each extracted report against gold requirements,
  independently of its overall verdict. It detects missing/extra material claims,
  wrong operators/values/modality/scope, invalid evidence, per-claim verdict errors,
  duplicate IDs and incorrect coverage. Matching uses quotes/attributes rather than
  generated claim IDs, so reordering does not count as an extraction error. Equivalent
  numeric units are accepted. Decision quotes are checked against the reference library,
  not merely the report's own copy of the decision text.
- UI mock reports regenerated by `npm run fixtures` (33 fixtures). This is generated
  test data, not a change to Bảo's UI components or API client.

No shared schemas, adapters, Forge manifest or dependencies were changed.
With Đạt's explicit approval after reviewing the live timeout, the evaluation-only
paths in `src/handlers/evalSuite.ts` and `src/handlers/worker.ts` were integrated

## Evaluation runner integration

The first live run exposed `FORGE_LLMS_TOKEN_LIMIT_EXCEEDED` (HTTP 429) for
`claude-sonnet-5`, with a limit of 500,000 tokens in the runtime error. The official
[Forge LLM limits](https://developer.atlassian.com/platform/forge/limits-llm/) describe
a 500,000-token-per-minute limit per model/installation; no daily reset time or
billing balance has been inferred from this error. The adapter has model fallbacks,
so the warning alone does not establish that a scenario failed.

The existing runner re-extracts all 10 decisions for each of the 30 scenarios: 330
extraction requests before repair or semantic calls. `eval/run-suite.ts` now exports
`runGoldenSuite(llm, options)`, a pure helper used by the eval handler:

```ts
// Current runEvalSuite implementation, after reading the existing model config.
return runGoldenSuite(new ForgeLlmAdapter(config.models));
```

- Decision extraction is cached only inside one invocation, using the engine's
  existing version-keyed cache port. With successful first-pass extraction, the 30
  scenarios need 10 decision + 30 ticket extraction calls, before semantic/repair
  calls. Gold constraints are never substituted for model output.
- Each row includes the strict `scoreScenario` results, observed successful models,
  operational errors, timing and claim counts. `passed` means strict pass;
  `verdictPassed` separately counts matching overall outcomes.
- The default 12-minute budget is checked between scenarios. `complete`, `evaluated`
  and `skippedIds` distinguish an interrupted run from accuracy failures. It cannot
  cancel an in-flight model call. An `LLM_UNAVAILABLE` report stops further scenarios.
- `onResult(scenario, report, score)` lets integration persist individual full reports
  or progress before the whole suite ends. Callback/storage failures propagate;
  persistence and retry/resume remain the integration owner's responsibility.

Three tests cover cache reuse/isolation, model-failure stopping, and exhausted time
budgets using the real engine with a fake model. Four additional worker tests cover
platform retries (including retry count zero), explicit first delivery, suite crashes,
and result-storage failure. The full `npm run check` passed (110 tests).

The worker now cancels an eval job on redelivery without calling the LLM again or
overwriting a newer result. A caught suite/storage failure cancels the job and records
an operational failure. Completed summaries include the batch's `requestedAt` to
distinguish runs. Only the eval branch changed; normal analysis retries are preserved.
Forge [automatically retries failed async events](https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/),
so GET polling and deployment do not cancel an invocation already in progress. The
guard stops its next delivery; an already running old invocation must finish or
time out first. The original runner's `pass` field checked only the overall outcome;
the new summary separates that count (`verdictPassed`) from strict `passed`.

Persisting full reports/progress remains optional follow-up: the current web trigger
returns the completed summary. The helper's `onResult` callback is available for this,
but no additional handler/storage files or endpoints were changed.

**Local observation correction:** PowerShell decoded `requestedAt` to a UTC
`System.DateTime`. Passing that object to `DateTimeOffset.Parse` lost its UTC kind
and interpreted it in local UTC+8, making the batch filter reject an already complete
report. Direct casting (`[DateTimeOffset]$result.requestedAt`) preserves the instant
and milliseconds. The comparison was reproduced (Parse: false; direct cast: true)
and the gitignored `.forge/read-eval.ps1` helper uses the corrected cast. The long
local wait must not be presented as LLM processing latency; the measured suite
duration is about two minutes. No additional live batch was requested after this run.

These are one-run results on 30 curated fixtures, not production accuracy estimates.
The call/model fields come from pipeline instrumentation and are not billing or
complete provider-request accounting. Live Jira/Confluence retrieval remains a
separate integration check.
